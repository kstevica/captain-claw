# Taskboard — plan

A kiosk (user mode) dialog that lists every task an agent received or sent on any
channel, tracks whether it was finished, by whom, for whom, with which parties and
with what result, and proposes next steps the user approves. Automatic, searchable
and filterable on every dimension, designed like the File library. Jev decides.

Branch: `feat/taskboard` (v0, v1 and v2 all land here, one commit + push per version).

## User decisions (2026-10-29)

| # | Question | Answer | What it means here |
|---|----------|--------|--------------------|
| 1 | Personal inboxes (own WhatsApp Web chats, Telegram inbox, all of Gmail)? | Yes, opt-in | v2: each one is off until the user switches it on in Taskboard → Sources, with consent text. Switching off deletes the tasks derived from it. Text inherits the source's retention (30 days). |
| 2 | May Jev close a task on its own? | Yes | `fulfilled ≥ 0.8` closes it (`closed_by = jev`) with Undo. The evidence badge still says whether a send/delivery was recorded. |
| 3 | Is a quick chat question a task? | Yes | Every admitted human turn is a task. Answered in the same turn on the user's own chat → done, result "answered in chat". It never enters Needs me. |
| 4 | Does an owner see members' tasks on a shared agent? | Not at all | A task belongs to exactly one board user (`user_id`). A member's turn on a shared agent goes to the member's board only. No owner view, no admin view. |
| 5 | Make non-mail sends on automated turns propose-only? | No | Existing automations keep working. Board-originated next steps always need a human click anyway. |
| 6 | Absorb Scheduled → All activity and follow-ups? | Link | Those views stay. The board ingests them as tasks and links back ("Open in Scheduled", "Continue in chat"). |
| 7 | History to fill in on first open | 30 days | v2 backfill from agents' `sessions.db`, last 30 days, marked historical, never proposes anything. |

## Principles

1. **Needs me first.** The dialog opens on "Needs me": what the user must decide, answer or confirm. Everything else is a view away.
2. **Evidence beats opinion, the user beats both.** Source statuses and recorded sends move a task first. Jev only picks among the moves the evidence allows. A user action (Done, Not a task, Snooze, Rename, Owes next…) applies at once and locks the field it touched; no machine pass overwrites a locked field.
3. **Jev decides, a model writes.** Jev answers typed questions (yes/no, choice, score) with calibrated probabilities. It cannot write a title, pull out parties or draft a reply — that is one extraction call per task on **the agent's own model** (owner tiers only as fallback).
4. **Strictly per user.** Every read is filtered by `user_id` on the server. The kiosk lock is UI-only, so the API is the boundary.
5. **Cheap first.** A deterministic gate (no model) runs before anything is judged. Jev and extraction have per-user daily caps; extraction tokens go through `usage_quota.record_tokens` and stop on `automation_blocked`.
6. **Nothing leaves without a click.** Email stays propose-only (draft). Every outward next step is a typed autonomy-ledger action with recipients from stored fields, approved by the user.
7. **Honest coverage.** A Sources sheet says what is tracked and what is not.

## Data model — `DATA_DIR/taskboard.db`

The whole schema is created in v0 so later versions only fill columns. Owner columns
have no FK to users (an auth-off deck uses the `local` user). Times are epoch seconds
(REAL). JSON columns are TEXT.

**tasks**
- `id` TEXT PK (`tb_` + 16 hex)
- `user_id` — the board this task belongs to (owner for own turns, the member for member turns)
- `agent_owner_id` — the agent's owner (cleanup only, never used for visibility)
- `agent_slug`, `agent_ref` (`runtime:slug:instance` when known), `agent_name`
- `title` (≤160), `ask` (≤600), `result_text` (≤600)
- `kind` — `request | sent | scheduled | proposal | follow_up | held_reply | link | todo | message`
- `direction` — `received | sent | internal`
- `channel` — first channel (turn_source key: `web, whatsapp, waweb, telegram, tg_inbox, gmail, device:<kind>, link, scheduled, autonomy, member, api, mcp, glasses, messenger`)
- `channels` JSON list — every channel the task touched
- `status` — `open | done | failed | dismissed | not_task | maybe`
- `owes_next` — `me | agent | them | nobody | unclear`
- `evidence` — `verified | claimed | none`
- `result` — `success | partial | failed | unknown | ''`
- `urgency` INTEGER 0–3, `due_at`, `snooze_until`
- `created_at`, `updated_at`, `last_event_at`, `closed_at`
- `closed_by` — `source | evidence | jev | rule | user | ''`
- `closed_by_party` — display name of who finished it (agent name, user, party)
- `fingerprint` (last event id + count), `extracted_fp`, `decided_fp`
- `triage_state` — `pending | ok | error | skipped`, `triage_error`, `triage_after`
- `user_locks` JSON `{field: at}` (a flag key the user set, e.g. `probably_done`, `low_confidence`, is locked by its own name)
- `flags` JSON (`contains_instructions`, `probably_done`, `stale`, `overdue`, `historical`, `answered_in_chat`, `failed_ack`, `why` (≤ 160, the latest decision's first reason); v1 adds `low_confidence` (admitted at Jev 0.65–0.8, left out of the badge), `expected_deliverable` (≤ 200, from extraction), `rule` (`mute` / `always_task`, the task rule that admitted it); v1.1 adds `own_chat` (the board user's own conversation with the agent, set by the ingest), `answered` (`yes | partly | no`, the extraction's reading of the reply) and `blocker` (≤ 160, why not), `agent_declined` / `partly_done` (rules: the reply couldn't, or did only part), `new_since_done` (someone wrote after it was done; v2: `new_since_ref`, the `source_ref` of the message the ingest flagged it for, and `close_waits`, the close or the "owes nobody" a source asked for while live work is merged in))
- `private` INTEGER (source turn held a member's data)
- `merged_into` TEXT, `source` (first adapter), `source_ref`
- `next_steps` JSON (candidates from extraction, v1/v2)
- `retention_until` REAL (passive sources)
- `search_text` — accent-folded haystack (`outbound_guard._fold`): title, ask, result, parties, agent, channel labels

Indexes: `(user_id, status, last_event_at)`, `(user_id, owes_next)`, `(user_id, agent_slug)`, `(agent_owner_id, agent_slug)`, `(merged_into)`, `(user_id, merged_into)` (a board's list costs what that board holds, not every board's unmerged tasks), `(user_id, triage_after) WHERE triage_state = 'pending'` (what the worker asks every 20 s). One task's parties are read by `task_id` (`+user_id` in the query: the People filter was quadratic by `user_id`; the test pins the plan).

**task_links** — `(user_id, key)` PK, `task_id`, `strength` (`strong | weak`), `created_at`.
Keys: `sched:job:<id>`, `sched:run:<id>`, `autonomy:<id>`, `fu:<id>`, `gmail:thread:<id>`,
`gmail:msg:<id>`, `link:<link_id>:<msg_id>`, `turn:<turn_id>`, `session:<agent_slug>:<session_id>`,
`cron:<agent_slug>:<job_id>` (v1.1: the agent's own cron job), `wa:<waid>`, `waweb:<chat_jid>`, `tg:<chat_id>`,
`todo:<agent_slug>:<id>`. v2 as built: an opt-in inbox's conversation is `tg_inbox:<chat_id>` (not `tg:`, so it never
meets an agent's bot chat), `waweb:<chat_jid>` or `gmail:thread:<id>` (+ `gmail:msg:<id>` per email); a board next
step is `autonomy:<id>` on the task it is about; a history turn is `turn:<sha256(history:slug:session:message)[:32]>`.

**task_events** — `id` INTEGER PK, `task_id`, `user_id`, `at`, `kind`
(`received | reply | sent | tool_call | delivery | status | proposal | approval | rejection | decision | correction | note`),
`channel`, `actor_kind` (`me | agent | party | system | jev`), `actor` (display), `summary` (≤500),
`source`, `source_ref`, `outcome` (`ok | error | blocked | ''`), `refs` JSON, `evidence` (`recorded | said | user | ''`), `private`,
`asks_nothing` (v2: 1 on someone's `received` message once Jev has said it asks the assistant nothing — written with `contains_instructions: false` on every such message on the task, it stays with the message wherever a merge or a split takes it, until a later `contains_instructions: true` takes it back (Jev changing its mind, or the rules failing closed: the next "no" has to read them again); `unread_words` is the rest, what no next step is made from).
`UNIQUE(source, source_ref)` makes every ingest idempotent.

**task_decisions** (v1) — `id`, `task_id`, `user_id`, `at`, `judge` (`jev | rule | model | user`),
`qset` (question-set version), `state_hash`, `answers` JSON (probabilities only), `applied` (transition text), `why`.

**parties** (v2) — `id` (`pt_` + 16 hex), `user_id`, `display_name`, `folded_name`, `kind` (`person | org`).
**party_handles** (v2) — `(user_id, kind, value)` PK, `party_id`; kind `email | waid | wa_jid | tg_id | fd_user | link`.
**task_parties** (v0 raw, v2 resolved) — `task_id`, `role` (`requester | doer | recipient | cc | mentioned`),
`kind`, `address`, `display`, `party_id` (v2), `verified` (header/register/speaker sources only),
PK `(task_id, role, kind, address)`. v2: a recorded (verified) row is linked to a person on an exact handle (an
email lower-cased, a number's digits, a WhatsApp jid of a phone also that number) or makes one; an unverified row
only finds a person someone else's handle made; the board user's own `fd_user` handle is never a person (it stays
`fd_user:<uid>`, "You"). Pre-v2 rows are linked once on open (`source_cursors` `v2:people`). People no task names
any more are forgotten (`_drop_tasks`).

**passive_marks** (v2) — `(user_id, source, task_id, what, ref)` PK: the links (`what` `link`, `ref` the key) and
parties (`party`, `ref` `[role, kind, address]`) an opt-in inbox put on a task, so switching it off or the text's
expiry takes exactly those off; merge, unmerge and split carry them along with what moved.

**task_rules** (v1) — `id`, `user_id`, `match` JSON (`sender | domain | channel | agent | job_id | source`), `effect` (`not_task | always_task | mute`), `created_from`, `hits`, `created_at`.

**turns** (v1, raw turn register) — `turn_id` PK, `agent_owner_id`, `user_id`, `agent_slug`, `session_id`,
`origin`, `origin_detail`, `channel`, `source`, `source_label`, `speaker_label`, `ext_refs` JSON,
`text_head`, `reply_head`, `deliverables` JSON, `outcome`, `started_at`, `ended_at`, `private`, `task_id`;
v1 adds `session_name`, `speaker_id`, `member`, `opener`, `human`, `literal`, `automation` JSON `{kind, id}`,
`tool_calls`, `failed_tool_calls`, `gate` (the gate's verdict, below), `task_key` (the link key that finds its task),
`open_ref` / `close_ref` (`boot:seq` each phase came under), `received_at`; v1.1 adds `own_chat` (the ingest's verdict, below).
Indexes `(received_at)`, `(gate, received_at)`, `(agent_slug, open_ref)`, `(agent_slug, close_ref)`.
Kept 30 days by `received_at` (each full sweep prunes, and so does the turn route at most hourly — the 30 days hold with the sweep off too; the tasks keep their `turn:` key).

**source_cursors** — `source` PK, `cursor`, `updated_at`.

**taskboard_settings** — `user_id` PK, `passive` JSON (`{telegram_inbox, whatsapp_web, gmail}` each `{on, consented_at}`),
`auto_close` INTEGER (default 1, decision #2), `jev_per_day` (200), `extract_per_day` (100), `counters` JSON (`{day, jev, extract}`),
`backfill_done_at`, `updated_at`. v2 cursors: `history:<uid>` (the backfill's counts and sentence), `passive:<inbox>:<uid>`
(each inbox's read), `agent_todos` (`{slug: max updated_at}`); `delete_user` drops them with the board.

## Lanes (computed, never stored)

- **Needs me** — `status=open` and not snoozed, and any of: `owes_next=me`, a linked proposal awaiting approval, a held reply, `flags.probably_done`, overdue; plus `status=failed` not yet acknowledged.
- **Waiting on others** — `status=open`, `owes_next=them`.
- **Agents working** — `status=open`, `owes_next=agent`.
- **Done** — `status=done`.
- **All** — everything except `not_task`, `merged_into` set; `maybe` shows under a "Maybe tasks" facet (v1).

Badge on the Taskboard tile = Needs me count (in v1 only tasks admitted at ≥ 0.8 count: those with `flags.low_confidence` stay in the Needs me list but are left out of `GET /summary`; v2: so are `flags.historical` tasks — history never notifies).

## API (user routes need `get_current_user`, filter by `user_id`, 404 on someone else's task)

- `GET /fd/taskboard/status` → `{sources: [{key, label, tracked, on, note}], counts: {needs_me, waiting, working, done, all}, sweep: {running, last_at, message}}`
- `GET /fd/taskboard/tasks?view=needs_me|waiting|working|done|all&q=&status=&channel=&agent=&direction=&kind=&party=&evidence=&result=&from=&to=&sort=recent|oldest|due|urgency&limit=&offset=`
  → `{items: [TaskItem], total, facets: {status, channel, agent, direction, kind, evidence, result, party}, counts}`.
  Facets are counted under the other filters (as in the File library). Multi-value filters are comma-separated.
- `GET /fd/taskboard/tasks/{id}` → `{task: TaskItem, events: [...], events_total, links: [...], parties: [...], decisions: [...], proposals: [...]}` (events = the latest 500, oldest first)
- `POST /fd/taskboard/tasks/{id}/action` `{action, value?}` — `done | reopen | dismiss | not_task | snooze (value = until epoch) | unsnooze | rename (value) | owes_next (value) | ack_failed | undo` → `{task}`. Each writes a `correction` event and locks the field. A closed task opened again (`reopen`, `not_done`, Undo of Jev's close) that nobody owed a move becomes the user's (`owes_next` me: back in Needs me). `undo` takes back the latest correction still holding a field — or, when Jev closed the task (`closed_by jev`) after it (or there is none), opens the task again as a correction of its own ("Undid Jev's close", status locked; Undo again puts Jev's close back). Every other action does what it says on a task Jev closed too.
  v1 adds `confirm_task` (a `maybe` task → open, owes the agent; an open `low_confidence` one → `low_confidence` false; locks `status` and `low_confidence`) and `not_done` (a task with `flags.probably_done`, or `done` → open, `probably_done` false, closing fields cleared; locks `status` and `probably_done`). Anything else they don't apply to is a 400. v1.1: opening a task again (`reopen`, `not_done`, Undo of Jev's close) sets `flags.new_since_done` false — the new message is what the user opened it for, so a later close doesn't say it again.
- `POST /fd/taskboard/sync` → runs the adapters now for this user (also run on dialog open). One sweep per user at a time and at most one per 2 s: calls while one waits join it, calls while one reads get the next.
- `GET /fd/taskboard/summary` → `{needs_me}` (cheap, polled by the tile badge every 30 s; v1: without `low_confidence` tasks).
- `GET /fd/taskboard/settings` → `{auto_close, jev_per_day, extract_per_day, counters: {day, jev, extract}, jev: {connected, source: own|team|""}, passive, backfill_done_at, updated_at}`; `counters` is today's (UTC) use, zeros on a new day. `PUT` takes any of `{auto_close, jev_per_day (0–2000), extract_per_day (0–1000)}` (400 outside the bounds) and answers like `GET`. (v2: passive sources with consent.)
- `GET /fd/taskboard/tasks/{id}/why` (v1) → `{items: [{at, judge: jev|rule|model|user, qset, applied, why, answers}], summary}`, latest first, at most 20: the `task_decisions` rows (extraction is judge `model`) merged with the user's own corrections (judge `user`, qset "", answers {}). `answers` by question id: `{p}` (yes/no), `{choice, p}`, `{score}` (urgency 0–3). `summary` says in a sentence or three why it stands where it is (v2: and, on an open task, that someone's message on it hasn't been read for instructions). 404 for someone else's task.
- v2 (as built; each module has its own router under `/fd/taskboard`, included in `server.py` after `taskboard.router`):
  - `POST /tasks/{id}/propose {kind?: auto|remind|ask_clarifying|reply_with_result|draft_email}` → `{proposal: ProposalView|null, reason}` (taskboard_nextsteps). 400 for another kind, 404 for someone else's task; a proposal of any source already waiting on the task comes back as it is ("A next step already waits…").
  - `PATCH /fd/autonomy/actions/{id} {text?, subject?, to?, channel?}` → `{action}` (autonomy_routes): only the owner (404 otherwise), only a `source='taskboard'` action still `awaiting_approval` (409 otherwise, and when an Approve/Reject wins the compare-and-set); 400 for a body that isn't a JSON object, a `to` not in `to_options` (email case-insensitive), empty or > 2000-char text, a subject > 200 chars, a channel nobody on the task is on, or a `to` and `channel` that disagree. Picking an email recipient makes it `mail.draft`, a chat one `reply.on_origin` (title rewritten). Approve / Reject stay `/fd/autonomy/actions/{id}/approve|reject`; what Approve dispatches is the row as last saved (read again once it is claimed, so a PATCH that landed just before counts and none can land after); Approve of a next step whose task closed, went, was merged away or was flagged `contains_instructions` meanwhile, or that waited 7 days, expires it (409).
  - `POST /tasks/{id}/merge {into}` → `{task}` (the task it is part of now — its id may differ from `into` when that was merged on), `POST /tasks/{id}/unmerge` → `{task, into}` (`into` null when the task it was in went with it: an inbox's task with nothing of it left), `POST /tasks/{id}/split {event_ids}` → `{task, new_task}`, `POST /tasks/{id}/not_same` → `{task}` (taskboard_threads). 404 when either task isn't the caller's; 409 when already merged / not merged / its target was merged on since (merges come apart in reverse order); 400 for merging into itself, splitting off every event, a correction or an event not on the task; 422 for empty `event_ids`.
  - `POST /backfill` → `{backfill}` (taskboard_backfill): starts the caller's history fill unless it runs or is done (then it only reports).
  - `GET /export?format=csv|jsonl&<the /tasks filters, view defaults to all, sort>` → a file (`Content-Disposition: attachment; filename="taskboard-<view>-<YYYYMMDD>.<format>"`, `Cache-Control: no-store`) of the caller's tasks only, at most 10,000, in the list's order: no `search_text`, fingerprints, `user_id`/`agent_owner_id`, and no deck user's id (an `fd_user` party is "You" or their name, address blank). CSV (UTF-8 with BOM) columns `id, title, status, lane, owes_next, kind, direction, channel, channels, agent, parties, ask, result_text, result, evidence, urgency, due_at, created_at, last_event_at, closed_at, closed_by, closed_by_party, why, historical, private, retention_until` (times ISO 8601 UTC; a cell starting with `= + - @` or a tab is prefixed with `'`); JSONL one TaskItem-like record a line (every party, `flags`, `proposal {id, status, title}`). A member's private text is only ever on their own board, so only they export it.
  - Detail `GET /tasks/{id}` gains `merged: [{id, title}]` (tasks merged straight into it) and `next_step_kinds` (what "Suggest next step" can ask for: `auto` and the moves with someone to reach; [] when it gets none or nobody on it can be reached). A merged task's own detail reads as itself (`task.merged_into` says where it went; its timeline holds only the merge note); the UI follows `merged_into`. `taskboard_threads.resolve` follows an id to the task it is part of now.
  - `GET /status` gains `backfill: {state: idle|running|done|error, done_at, progress: {agents_done, agents_total, turns, tasks}, message}`; it starts the fill on the first look only while the board's background work runs (`taskboard.start()` ran, `FD_TASKBOARD_DISABLED` unset), a failed run waits for `POST /backfill`. Sources rows: `history` (tracked while running or done, its note how it stands), `agent_todos` (tracked, after `agent_chats`), and the three inboxes (`telegram_inbox`, `whatsapp_web`, `gmail_inbox`) tracked while switched on.
  - `GET /settings` `passive` = `{telegram_inbox|whatsapp_web|gmail: {on, consented_at, available, note}}` (`available` false with a note saying what to connect: the Telegram inbox collecting, WhatsApp Web linked, Google connected with Gmail read). `PUT /settings {passive: {<key>: {on: true, consent: true}}}` switches one on (no consent, an unknown key or an unavailable inbox: 400 — every switch is checked before any moves); `{on: false}` switches it off and deletes what it put on the board; with `passive` the answer is `{settings, deleted}` plus the settings' fields at the top level, as without it.
- Agent route (v1): `POST /fd/taskboard/agent/turns` (agent auth exactly as `/fd/tool-audit/agent/calls`: `tool_audit_routes._identify`, the `X-Agent-Auth` token) — body and records in v1 item 1, → `{ok: true, accepted}`.

`TaskItem` = the task row minus `search_text`/fingerprints, plus `parties` (first 5), `lane`, `proposal` (`{id, status, title}` when a linked autonomy action is waiting), `links` (`{scheduled_job_id, session_id, autonomy_id, followup_id}`) and `agent_name`.
v2: `proposal` is a ProposalView — `{id, status, title, kind (the catalog's mail.draft | reply.on_origin for a tool action, else the ledger's kind: nudge…), source ("taskboard" | the arbiter's), editable (a taskboard one still awaiting approval), payload: {text, subject, to, to_options: [{address, display, kind}], channel}}` (an Autonomous Work proposal shows its args' body/subject/to and no `to_options`); `taskboard._waiting_proposals` is `taskboard_nextsteps.waiting_proposals`, which first expires the user's next steps whose task closed, went, was merged away or was flagged, or that waited 7 days. `parties[]` carry `party_id` and `name` (the person's, "" when unresolved); facets `party` ids are `party:<party_id>` labelled with the person's name, an unresolved handle keeps `<kind>:<address>`, and the filter takes both forms. `flags` may carry `same_as {task_id, title, p}` and `historical`; `retention_until` is set on inbox tasks.
v1.1: every party in `TaskItem.parties` and the detail's `parties` carries `me` (kind `fd_user` and address = the board user's id; the UI says "You" and never shows a deck user's id), and each person is listed once: a party a model read out of the text (unverified, kind `email | phone | telegram | name`) is left out when its folded display name is a recorded party's, or one read before it (an address wins over a bare name).

Approve / Reject of a linked proposal call the existing `/fd/autonomy/actions/{id}/approve|reject`. A held Gmail auto-reply uses the existing auto-reply approve route — on its own `held_reply` task, or on the request task whose thread it is on (its latest auto-reply event is `held`).

## UI — `TaskBoard.tsx`

Same frame as `FileLibrary.tsx`: `KioskWideDialog label="Taskboard" widest`, header (icon chip, title, subtitle, sync status, Sync now, FullscreenButton, Close), toolbar (debounced search, sort select), three columns on desktop — facet sidebar (w-56), list, detail pane (w-[380px]); single column on a phone with the detail as an overlay ("← All tasks") and filters in a full-screen sheet.

- **Next move** is the board's own menu (`NextMoveMenu`), not a browser select: it opens upwards from the bottom of the task, with an icon, a tick on the current one and a digit for each.

People are made and joined only on exact handles of recorded rows (Gmail headers, waid, WhatsApp Web jid, positive Telegram id, deck users, linked systems); names only from records — a deck user's own name and email (`users`) and, on the agent owner's own board only (never a member's), the agent's address book (`sessions.db` `contacts`, read-only, private contacts skipped; one contact holding an email and a phone makes them one person). Never a name match or a model's guess. The board user's own handle is never a person ("You"). People's names join the search text. Naming runs where records go through `attach_or_create` (agent turns, the Gmail adapters); other adapters' parties are linked by exact handle as they are written.
4. **Opt-in inboxes** (`taskboard_passive.py`: no router, the settings and status routes call it; three sweep adapters run last). Off until switched on with consent (`consented_at` kept; the UI shows the consent text), and only once the channel is connected. Only each switched-on user's own data, from a cursor of its own, never waking an agent: the Telegram inbox (`telegram_inbox_*`, unsealed with `fd_crypto`), WhatsApp Web (`<data>/whatsapp_web/<uid>/store.sqlite3`, read-only) and Gmail (the user's own token on the deck's event loop, `messages.list after:` paged up to 500 ids, then `format=full` of the oldest 50 not read yet a pass — the newer rest next pass; a list that stops short keeps the cursor and drains what it didn't reach first, `before:` where it stopped; never gws, never an agent). Switching on reads back the last day.
   - The gate (no model): a group only when someone replies to the user or @mentions them; never status broadcasts, channels, stickers or deleted messages; Gmail through `gmail_inbound.prefilter` with the switch-on time as `enabled_at` (window, label, own-mail and empty codes always skipped, the rest unless an `always_task` rule says otherwise, `too_long` passes); then the user's `task_rules` (`taskboard_ingest._rule`).
   - Someone's message → a task kind `message`, direction received, channel `tg_inbox` / `waweb` / `gmail`, **status `maybe`** (owes me) until Jev's `is_task` opens it (or the user's "Yes, it's a task", which leaves it the user's to answer) — so a chat's every "ok" never reaches Needs me — with `flags.contains_instructions` until Jev says it asks nothing of the assistant (fails closed), `private`, triage pending. Triage reads kind `message` as it reads a request (extraction on the board user's own tier — it has no agent — and Jev; rules alone leave it a maybe and only fail it closed); it never gets a next step. A conversation is one task while it goes on: a chat's messages within 12 h of each other, an email thread while its task is open, maybe or not a task; a thread another source holds (an agent's request, a follow-up, a held reply) gets a `received` event there (v1.1's inbound-after-done applies). A chat's key a merge or a split moved to another task follows the same 12 h rule: a message or the user's own word after the gap, or on a task closed since, makes a task of its own and takes the key (`_live`, `passive_write(release=)`), so one old task never swallows a chat for good.
   - The user's own message → a `sent` event (actor me, recorded) on the conversation's task (an open message they owed now owes them), else a `sent` task, done. An agent's send is never the user's own (`sends.wa_id`; Gmail via `gmail_sends`, the auto-reply's sent id, tool-audit `refs.gmail_message_id`, the `gmail:msg` key); the user's own messages are read 2 min (WhatsApp) / 10 min (Gmail) late, so the agent's records are there first.
   - Who an email names: only its authenticated sender is verified. Its To and Cc are written by whoever wrote the email, so they go on the task unverified (`mentioned` on an own chat) and are never a next step's recipient (unlike the headers of the user's own sends).
   - Retention: text cut (ask ≤ 600, event ≤ 500); every inbox task and event carries `retention_until` = the message's time + 30 days (less when the inbox keeps fewer); older messages are never read, expired ones purged by the sweep. Switching off, the inbox going away where it lives (Telegram inbox off, WhatsApp unlinked or logged out) and expiry take off exactly what the inbox made (its events by source, its links and parties by `passive_marks`): a task left with no events goes, and so does one an inbox made with only the user's own notes left (a merge, a split, a Done: unless they named it, a title they gave it stays), at the unmerge that leaves it so too (`_passive_emptied`: the inbox may never run again); a mixed task keeps the rest and, when an inbox made it, is retold from what is left (what the user did on it stays, and titles it only when nothing else can), once: `retention_until` empty says nothing of an inbox's is left to tell, so what a pass writes on it later is no later expiry's to wipe — another inbox's message merged in names it then, and it is that inbox's from there on (`source`, `retention_until`), gone with that one's text; a task it made that was merged into another is retold from what is left of the messages its merge moved (it stays merged, Unmerge still there), or goes with them — and then what its merge did goes too, as an unmerge's would (`_merge_over`: the target closed again and unflagged as far as nothing else merged in holds it, read again, on along a chain); every other task holding its marks with nothing of it left where its events went (one a merge chain passed through) gives up its links and parties too. The user's merge / unmerge / split / "not the same" notes naming such a task are told without its title, its corrections keep none of its text (`before`), a merge or split note lists no link or party nothing on the board holds any more (`_passive_clear_notes`: a conversation's key, someone's number or address), a party a model read out of an inbox's task is that inbox's wherever a merge copies it, and a person keeps no name only an inbox row gave them.
5. **History** (`taskboard_backfill.py`, decision #7). Once per board (the first `GET /status` while the background work runs, or `POST /backfill`), a background job reads each caller agent's `DATA_DIR/<slug>/data/sessions/sessions.db` read-only (`mode=ro`, a short busy timeout; a busy file is skipped and named), never waking the agent, for the last 30 days up to the first turn the agent's register keeps (from then on the turns are the register's), the newest 2000 turns per agent at most. Turns go through v1's own gate (`_board`, `_gate`, `_reply`), so code-made openings, automations, rules and member routing behave as live (decision #4: the owner's sessions to the owner, a member's to the member while they are one, never the other way). A Telegram user's own session (`tg-<name>`) holds no chat id: the agent's `app_state` (`telegram_user_sessions`, else a `tg-` name only one approved user has) names the account, so a member's linked Telegram lands on the member's board as live; one whose account can't be told is passed over. A history turn makes a task of its own (never attached to a live one), and only a task it made is marked historical. Two first looks at once start one job. **Differs from the plan:** history spends no caps, no Jev and no extraction — every task is `flags.historical`, sorted at once by the rules (a `rule` decision, `triage_state ok`), never queued; a turn that never got a reply is open, owed by nobody (All only). No proposal, no notification, not in the badge. A run again adds nothing (`turn:` keys); one cut short by a restart starts again on the next open; `taskboard.stop()` stops a running one.
6. **Agent todo lists** (sweep adapter `agent_todos`, in `taskboard_backfill.py`): each `todo_items` row a task kind `todo` (`todo:<slug>:<id>`, direction internal, no channel, triage skipped, urgency high 2 / urgent 3) on the board of the session that made it (a member's while they are one, never the owner's) — else its target session's, else (no session named) the agent owner's; a member's items private. A session deleted since is told by the agent's `saved_attribution.db` `member_sessions` (kept when a session goes; one never recorded there is the owner's); that record unreadable → on no board. `done` → done (evidence claimed, closed by source); pending / in_progress → open, owed by the agent, or by the user when `responsible` is human; `cancelled` (also what `archive_old_todos` makes of old done items) → dismissed, or done when `completed_at` is set; an item gone from the list → dismissed. The first read takes open items and anything touched in the last 30 days.

## Safety rules (all versions)

- Inbound text (mail, messages, link payloads) is untrusted: fenced in every prompt, never used as an instruction, and neither a task flagged `contains_instructions` nor a task holding someone else's message Jev hasn't said asks nothing of the assistant — on whatever task it landed — ever gets a proposal.
- Recipients of a next step come from stored task fields (parties with `verified=1` — never what an inbound email's own To or Cc says — and v2 the turn's own recorded origin for a chat reply, only where it is provably the asker's alone: never a bus channel others may be on), never from model text; dispatch checks them against the proposal's `to_options` again.
- Email is drafts only. Board proposals never auto-dispatch; only a human Approve runs them, through the existing guards (`mail_authority`, `gmail_send_routes`).
- Member content stays on the member's board; extraction and Jev for a member task use the member's allowance and the member's own or team Jev key.
- No admin/owner view of other users' tasks.

## Verification and shipping (each version)

- Python tests from a neutral directory with `PYTHONPATH=<worktree>` and the `os._exit` plugin (see the test-baseline notes); diff failure sets against main for touched packages.
- `cd flight-deck && npm run build` (the worktree symlinks the main checkout's `node_modules`), prune orphan assets so `static/assets` keeps only what `index.html` and `hud.html` reach, and walk both import graphs.
- Live check on a scratch deck (auth on, a kiosk member + owner, seeded ledgers; a fake LLM and a Jev stub for v1/v2) in the browser pane, desktop and phone width, both themes.
- Deploy: FD restart + hard refresh (v0); agent restarts too (v1/v2, turn register and tool-audit refs; v1.1 also `ws_handler` and `prompt_execution`, which name an automation's id for the turn; v2 `web/ws_handler.py` and `turn_register.py`, which keep a device's or a Messenger person's `turn_origin` — everything else in v2 is Flight Deck's).
